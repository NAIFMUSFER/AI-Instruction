# Independent job-boundary review — 2026-11-10

Read current migration 02, workspace HTTP/job orchestration, provider budget/progress IPC, canonical write fencing in migration 03, and their executable regression tests. This is selected deep review of those boundaries, not a claim that all backend code was reviewed.

Three material issues were found and corrected collaboratively before the DB-dependent PR was finalized:

1. **Paid work could precede durable accounting.** The child emitted provider-call progress over a one-way pipe and immediately advanced to outbound work. A failed parent database update could leave resumable work with an undercounted budget. The process runner now waits for a parent acknowledgment; the parent sends it only after the durable progress callback returns, within the operation deadline. Unknown/store/transport failures are excluded from the explicit resume allowlist. Three real-process regressions pass: denied accounting produces no outbound marker, outbound work observes committed accounting, and delayed accounting past the deadline cannot release outbound work. These are synthetic markers, not paid calls.
2. **Committed results and job state could disagree.** A successful canonical append and separate job-finish call left a window where cancellation or expiry could mark the job failed even though its revision was durable. Polling then used a note scan that could transiently claim success before a later poll returned interruption. Migration 03 now writes canonical revision and exact job SUCCEEDED/revision ID in the same transaction while holding the lease row. Finish is idempotent for that exact result; subsequent cancellation/expiry preserve success. Synthetic note-based status recovery has been removed from the new path. The lease-bound write also binds expected head and exact task marker.
3. **Lease checks used a clock captured before lock waits.** Job mutation now refreshes the database clock after row/advisory waits and after the project lock for admission, and rechecks capability expiry. Thus it cannot authorize a heartbeat using an old pre-wait time. Membership rows are locked FOR SHARE during job and canonical mutations, serializing role removal/demotion with admitted work.

Independent rerun: **53 PostgreSQL boundary assertions + 37 PostgreSQL lease assertions passed** on PostgreSQL 16.2 standalone. These cover role restrictions, revoked direct table writes, same-ID replay and mismatched fingerprints, one healthy project worker, wrong lease, monotonic budget, explicit cancellation, late append rejection, expired work, disallowed uncertain resume, one resume per source, atomic completion, and terminal-state preservation. IPC acknowledgment tests separately passed all three cases.

No guest or cross-project mutation bypass was found in the reviewed path: a real user JWT, matching signer actor/purpose/project, current owner/editor role, and SQL CAS/lease checks are required. A forged project/job ID alone cannot invoke the backend capability or bypass RLS. Public and private legacy canonical write functions and direct job mutation grants are revoked by the activated migrations.

Remaining limitations and release prerequisites:

- Tests execute a real isolated PostgreSQL engine with synthetic auth scaffolding. They do **not** prove real Supabase JWT/PostgREST configuration, actual production grants/migration state, or concurrent lock contention across two live database connections/replicas. Those remain required integration checks before activating this DB-dependent increment.
- A provider request already accepted before cancellation/revocation cannot be recalled. Subsequent provider calls require a new durable progress acknowledgment; no automatic uncertain retry is claimed.
- The current heartbeat coroutine stops after its first unhandled transient persistence error. This fails closed and cannot revive an expired worker, but a long otherwise healthy provider call may lose its result if the lease expires. A bounded heartbeat recovery policy remains an availability improvement to validate with real network-failure tests.
- The actual ACS database and signer provisioning are unavailable in this session. These changes remain **not deployed**, separate from the independently deployable frontend/geometry release.
