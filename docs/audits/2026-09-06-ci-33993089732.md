## Evidence and diagnosis

At 21:48:04 UTC the failing target reported `GL: null · null`, then 1,263 attempted draws with one distinct pixel color, `100%` non-background pixels and a zero frame hash. The normal model, deliberately NaN geometry and replacement model all produced that same zero buffer. Five assertions rejected it; two weaker small/mobile assertions incorrectly accepted its non-background percentage alone.

The WebGL context object was treated as sufficient proof of availability. There were no context-loss or GL-error checks before drawing or reading pixels. A lost context can remain truthy while queries return null and readback leaves an initialized buffer unchanged. The WebGL specification explicitly requires `isContextLost()` to track this condition; its one-shot `CONTEXT_LOST_WEBGL` error can subsequently become `NO_ERROR` while the context is still lost. [Khronos specification](https://registry.khronos.org/webgl/specs/latest/1.0/#5.14.13).

Both raw-WebGL targets also selected the legacy `--use-gl=swiftshader` backend. Chromium documents the driver selection as `--use-gl=angle --use-angle=swiftshader`. The patch uses that documented configuration. The historical log is consistent with context loss but did not record the loss event or GPU process diagnostics, so the exact driver-side trigger of that loss is **NOT VERIFIED**. [Chromium SwiftShader documentation](https://chromium.googlesource.com/chromium/src/+/main/docs/gpu/swiftshader.md).

A separate evidence defect was found: both targets always override Three.js with `lib_gl_three.js`, but claimed real Three.js execution when its vendor file existed. The benchmark also wrote `three_js_real: true` based on file existence. Presence of an unused library is not runtime evidence. The patch reports the adapter actually loaded; the independent shipped-page test remains the evidence for real Three.js rendering.
